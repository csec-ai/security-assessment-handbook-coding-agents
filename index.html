Agentic AI Coding Assistants
Introduction
Background and context for this security assessment handbook.

Artificial Intelligence (AI) is being applied across sectors to drive efficiency and innovation. To reap the benefits of AI, users must have trust and confidence that the AI will function as originally intended, and outcomes are secure. To secure AI systems, the Cyber Security Agency of Singapore (CSA) has released the Guidelines and Companion Guide on Securing AI Systems in Oct 2024. The Guidelines are designed for system owners to secure the use of AI throughout its life cycle, and the Companion Guide complements the Guidelines as a useful reference that contains practical measures and controls that system owners may consider implementing.

Subsequently, the advent of Agentic AIAI systems that can independently plan and execute multi-step tasks to achieve a specified objective, using tools and data with minimal human intervention per action. capabilities, which can understand context, formulate plans and take independent actions to achieve specified objectives, also introduces new risks with greater potential for impact given its added capabilities and access to tools and data. As such, CSA has released the Addendum on Securing Agentic AI in Jun 2026 to outline how risks could be identified and assessed based on capabilities of Agentic AI systems as well as practical controls to mitigate relevant risks across the development lifecycle.

Based on the Addendum, CSA has since performed a deep dive into AI Coding AssistantsAI coding assistants that go beyond generating code suggestions. They can plan multi-step tasks, invoke external tools, read and write files, execute commands, and interact with remote services with minimal human intervention per action., which is an agentic AI use case commonly adopted by developers. We leverage the Guidelines and Addendum to develop a security assessment approach of coding assistants, and recommend relevant mitigations associated with their use. By doing so, we intend to help security practitionersProfessionals responsible for assessing, monitoring, and managing cybersecurity risks within an organisation. This includes security engineers, analysts, architects, and risk managers. and developersSoftware engineers and technical staff who build, maintain, or operate systems that use agentic AI coding assistants as part of their development workflow. adopt AI Coding Assistants more securely.

About This Handbook

CSA developed this handbook to apply the Addendum's guidance to a specific agentic AI archetype: the AI coding assistant. It covers the system architecture of common deployments, identified attack vectors with adversarial attack paths mapped to MITRE ATLAS tactics and techniques, and mitigations applicable at each trust boundary.

Baseline Attack Vectors

The following attack vectors (T-001 to T-006) form a baseline set for IDE-based and CLI-based agentic AI coding assistant deployments. Each is detailed in the Attack Path tab with step-by-step adversarial chains and applicable mitigations. Treat this baseline as a starting point for assessment and extend it with vectors specific to your organisation's deployment, tooling, and threat environment.

T-001
Instruction file with malicious prompts
Malicious prompts embedded in instruction files in cloned repositories direct the agent to execute attacker-defined actions. Applies to IDE and CLI agents.
T-002a
Malicious remote MCP server
A spoofed or attacker-controlled remote MCP server is configured in place of a legitimate one, injecting malicious tool responses into the agent context. Applies to IDE and CLI agents.
T-002b
Compromise of benign remote MCP server
A legitimate, already-trusted remote MCP server is compromised by an attacker who embeds malicious behaviour into its tools, exposing all users without any configuration change on their part. Applies to IDE and CLI agents.
T-003
Compromised local MCP server
A trojanised local MCP server package exfiltrates sensitive files when the coding assistant grants it filesystem access during project initialisation. Applies to IDE and CLI agents.
T-004
Malicious prompts in information sources
Prompt injection payloads embedded in external content (e.g. GitHub Issues, documentation) are fetched by the agent and executed as instructions, planting an executable script that runs automatically on the next commit, or exfiltrating data. Applies to IDE and CLI agents.
T-005
Skills with malicious instructions
Malicious skill packages published to public repositories embed adversarial instructions that, when loaded into a CLI-based coding agent, direct the agent to exfiltrate credentials or establish persistence. CLI agents only.
T-006
Hooks with malicious actions
Repositories pre-configured with malicious lifecycle hooks in settings.json automatically execute attacker payloads when a user clones the repo and triggers an agent session event. CLI agents only.

Control levels: Each control is categorised into three levels based on criticality, with Level 0 the most critical.

How to interpret these controls

The mitigations listed in this tab are reference controls intended to achieve the identified security objective for each attack vector and trust boundary. Organisations may implement equivalent or compensating controls based on their architecture, operating model, and risk appetite, provided the resulting risk is assessed and accepted appropriately. An Attack Vector value of "All" means the control is broadly applicable across attack vectors, not that it is universally mandatory. Each control carries a stable identifier, M-001 onwards, which stays with that control across versions of this handbook so it can be cited in procurement requirements, audit evidence, and remediation tracking.

Note: Where a reference mitigation is operationally impractical, assessors should document the alternative control, its expected risk reduction, and the resulting residual risk.

Attended and unattended deployments: The controls in this tab assume an attended deployment, in which a developer initiates the session and is present while the agent works. Three Level 0 controls depend on that presence. Select any of them to open the control, where its compensating substitute is shown.

  • M-011Human verification before agent-initiated file changes or commands take effect
  • M-015Immediate interruptibility of the agent at any point during execution
  • M-019Human approval before a new skill, hook, or external component is activated

In an unattended deployment, where the agent is triggered by a pipeline event, an issue assignment, or a schedule, those three cannot be implemented as written and require the compensating substitutes shown against each of them. Because these controls carry a substantial share of the overall risk reduction, the residual likelihood ratings in this handbook should not be read across to unattended deployments without reassessment.

Risk Assessment
This tab provides the reference risk matrix and scoring scales for rating the severity of the attack vectors identified in this handbook. Combine an impact score with a likelihood score to arrive at a risk rating (Low, Medium, Medium-High, or High) for a given attack scenario.

How to rate a risk

  1. Define the risk scenario. Take one attack vector from the Attack Path tab and describe how the threat event could affect the agent in your environment, including what the agent could be induced to do and the resulting adverse consequence. Assess one scenario at a time. It is useful to first record the capabilities of the agent in your deployment using the Capability Checklist below, as these determine which attack vectors are relevant and how far their consequences reach.
  2. Assess impact. Work down the Impact Scale and take the highest rating where any single criterion is met. Determine the impact based on the potential consequence in your deployment, taking into account the capabilities of the agent, and the assets, systems and data that the agent can access or affect. This is why the handbook does not assign an impact rating to individual attack vectors.
  3. Assess likelihood. Assess the likelihood that the threat event could successfully occur under the conditions of your deployment. Rate the scenario against all three dimensions of the Likelihood Scale and take the lowest of the three, as the attacker must satisfy all three for the attack to succeed. The likelihood ratings shown for each vector in the Mitigations tab provide a starting reference and should be adjusted to reflect your deployment context.
  4. Determine inherent risk. Use the risk matrix to determine the inherent risk rating from the assessed impact and likelihood, before taking controls into account.
  5. Apply recommended mitigations and determine residual risk. Apply the relevant controls from the Mitigations tab and reassess the likelihood and impact, where applicable. Use the risk matrix to determine the residual risk and record both the inherent and residual risk ratings.

Likelihood Scale
Each likelihood level is defined across three dimensions: Discoverability, Complexity, and Repeatability. An attacker must satisfy all three, so the rating is set by the binding constraint: score each dimension, then take the lowest. Complexity of exploit is scored by how hard it is to mount an attack that reliably achieves its objective, not by how few steps are needed to attempt one.
Likelihood Discoverability of exploit Complexity of exploit Repeatability
Almost Certain (5) Vulnerabilities can be discovered from publicly available information Trivial, a straightforward attack achieves its objective on essentially every attempt with no tailoring The attack can be repeated any time
Likely (4) Vulnerability can be discovered through functional use of the application Reliable once the attack is placed correctly and lightly tailored to the target's setup; minimal tuning The attack can be carried out frequently
Possible (3) Vulnerability can only be discovered with technical specification of the application Needs specific conditions, placement, and a few attempts to land, succeeds sometimes, not every run The attack can only be carried out at specific times
Unlikely (2) Vulnerability can only be discovered through technical analysis of the application Requires obfuscation (Unicode / zero-width, encoding) or an attack hand-tuned to one specific agent, tool, or configuration The attack can only be carried out infrequently
Rare (1) Vulnerability can only be discovered through source code analysis of the application Only works via multi-step chaining with other exploits or a precise, tightly sequenced setup The attack can only be carried out once

Non-determinism check: Where an attack depends on how the model responds to attacker-supplied content, the outcome is probabilistic, and the same attack can succeed on one run and fail on the next. This is why Complexity is scored on reliability of success rather than ease of attempt: an attack that only lands occasionally sits at Possible (3) or below, not Almost Certain. As more evidence accumulates through repeated trials, revise the level up or down accordingly.

Unattended deployments: the residual likelihood ratings assigned to each attack vector assume an attended deployment with a developer present during the session. Where an agent runs unattended, three Level 0 controls are replaced by weaker compensating substitutes: M-011 human verification, M-015 immediate interruptibility, and M-019 approval before activation. Residual likelihood should be reassessed upward accordingly rather than inherited from this handbook.

Frequently Asked Questions
Common questions about the scope, content, and application of this handbook.
About This Handbook
Who is this handbook for?
This handbook is intended for security practitioners and developers who are assessing, deploying, or securing agentic AI coding assistants in an enterprise environment. It assumes some familiarity with software security concepts, though the Introduction tab is designed to be accessible regardless of technical background.
How does this relate to the CSA Addendum on Securing Agentic AI?
This handbook is intended to be read alongside the CSA Addendum on Securing Agentic AI, which provides broader guidance on securing agentic AI across different system types. This handbook applies that guidance to a specific archetype (the agentic AI coding assistant), with concrete trust boundaries, attack vectors, and mitigations specific to that deployment context.
Does this apply to all AI coding assistants, or only specific products?
The handbook is applicable to agentic AI coding assistants that can invoke external tools, read and write files, execute commands, and interact with remote services. It is not specific to any product. The two deployment archetypes (IDE-based and CLI-based) are representative of how most commercial and open-source agentic AI coding assistants are deployed today.
Will the attack vectors be updated over time?
Yes. T-001 to T-006 form a baseline set: a representative, currently identified group of attack vectors, not an exhaustive threat model. Treat this list as a floor for assessment, not a ceiling: as deployment practices evolve and attacker techniques mature, additional vectors may be identified and included.
Technology and Scope
What is the difference between an IDE-based and CLI-based coding agent?
IDE-based coding agents are integrated directly into a developer's code editor, providing assistance within the editing environment. CLI-based coding agents operate from the terminal and have direct access to the local filesystem, shell commands, and lifecycle hooks. CLI-based agents generally have a broader attack surface due to their deeper system access and support for skills and hooks, which introduce additional extension points not present in most IDE-based deployments.
Why is insecure code generation not included as an attack vector?
Insecure code generation arises from the limitations of the underlying model. It is an outcome of how the model was trained, not the result of an active adversary exploiting the system. This handbook is scoped to adversarial attack vectors, where an attacker deliberately manipulates the agent's inputs to cause harmful actions. Guidance on managing model output quality, including insecure code generation, falls within the broader CSA Addendum on Securing Agentic AI.
Are all attack vectors equally likely to be exploited?
No. Each attack vector has an assessed likelihood of exploitation before and after mitigations are applied, visible in the Mitigations tab when filtering by a single attack vector. In general, vectors that rely on a developer cloning a malicious repository or connecting to an attacker-controlled server have a higher likelihood than those requiring compromise of an already-trusted service.
Deployment
Does this apply to cloud-hosted deployments, on-premises deployments, or both?
Both. The attack vectors and trust boundaries described in this handbook apply regardless of whether the underlying LLM is accessed via a cloud API or hosted on-premises. The key factors are the capabilities of the coding agent (what tools it can invoke, what files it can access) and the trust boundaries in the deployment, not the hosting model of the LLM itself.
My organisation does not use MCP servers. Which attack vectors still apply?
T-002a, T-002b, and T-003 (the three MCP-related attack vectors) would not apply directly. T-001 (Instruction file with malicious prompts), T-004 (Malicious prompts in information sources), T-005 (Skills with malicious instructions), and T-006 (Hooks with malicious actions) remain relevant depending on the features enabled in your deployment. You can use the Architecture tab to filter by attack vector and see which components are affected.
Does this handbook apply to agents that run without a developer present, such as CI/CD-triggered or scheduled agents?
Yes, subject to one qualification. The architecture is unchanged: an agent triggered by a pipeline event, an issue assignment, or a schedule uses the same components and crosses the same trust boundaries (TB1 to TB6) as one driven by a developer at a workstation, and every attack vector remains applicable. The difference lies in the principal on TB1. In an attended deployment that principal is a person; in an unattended deployment it is a pipeline trigger operating under a workload identity, which should be distinct from any individual developer's credentials so that the agent's authority can be scoped and revoked independently.

Three Level 0 controls assume a developer is present, and cannot be implemented as written where one is not. Select any of them to open the control in the Mitigations tab, where its full compensating substitute is shown.
  • M-011Human verification before agent-initiated file changes or commands take effect. Per-action approval is replaced by pre-merge review. The agent works on a branch and submits its output through a pull request that it cannot approve or merge.
  • M-015Immediate interruptibility of the agent at any point during execution. Human interruption is replaced by automatic bounds: a hard run timeout, caps on tool and API calls, and independent run-level cancellation.
  • M-019Human approval before a new skill, hook, or external component is activated. Activation is determined before the run rather than during it. Dynamic activation is disabled and the permitted component set is pinned in a source-controlled manifest.

Because these three controls account for a substantial share of the overall risk reduction, the residual likelihood ratings in this handbook assume attended operation. Unattended deployments should reassess residual likelihood rather than inherit it.
How do I know which trust boundaries are relevant to my deployment?
Use the System Architecture tab to review the trust boundary model for IDE-based and CLI-based deployments. Each trust boundary is labelled (TB1 to TB6) and describes the components it separates and the risks it introduces. Boundaries that involve components your organisation does not use (for example, TB4 and TB5 if you have no local MCP servers) can be deprioritised. The Mitigations tab can also be filtered by trust boundary to focus on relevant controls.
